## El problema

Los entrenadores personales necesitan crear rutinas desde la computadora (pantalla grande, teclado, comodidad) pero sus clientes las consultan desde el celular en el gimnasio — donde frecuentemente no hay WiFi o los datos móviles son un desastre. La posta es que ninguna app de fitness resuelve bien las dos cosas: authoring en desktop y consumo offline en mobile.

## La solución

FitCoach es un monorepo con **Turborepo** y **pnpm workspaces** que comparte un paquete de tipos entre tres apps: mobile (Expo), desktop (Tauri v2 + React + Vite), y un paquete compartido (`@fitcoach/shared`) con tipos, constantes, validación e i18n.

La decisión más importante del proyecto: **SQLite es la source of truth, no Supabase**. Todo se escribe primero en SQLite local con Drizzle ORM, la UI se actualiza instantáneamente (optimistic UI), y un sync service en background pushea los cambios a Supabase cada 5 minutos o cuando vuelve la conexión. El pull trae los cambios remotos y hace upsert en SQLite.

Cada tabla tiene campos `pendingSync` y `syncedAt`. Cuando el usuario modifica algo, se marca `pendingSync: true`. El sync service busca todos los registros pendientes, los pushea a Supabase, y si tiene éxito los marca como sincronizados. El orden de sync importa: primero profiles, después trainer_clients, después routines, routine_days, exercises, y al final exercise_logs. Si sincronizás un hijo antes que el padre, Supabase te rebota por foreign key.

## Stack y decisiones clave

- **Turborepo + pnpm workspaces**: El monorepo tiene `apps/mobile`, `apps/desktop`, y `packages/shared`. Turbo cachea los type-checks y lints entre apps
- **Drizzle ORM + expo-sqlite**: TypeScript-first ORM que genera queries tipadas. Los IDs locales se generan con `Date.now() + random` porque SQLite no tiene UUID nativo
- **Zustand v5 para estado**: 5 stores (auth, routines, sync, settings, subscription). Sin providers, sin boilerplate, integración directa con SQLite
- **RevenueCat desde el día 1**: Freemium con 3 clientes gratis. La verificación del límite está en `canAddClient()` antes de cada operación, no como un check cosmético
- **Tauri v2 para desktop**: Rust backend con React frontend. Sin offline-first en desktop (conexión estable asumida), Supabase directo
- **NativeWind v4**: Tailwind CSS en React Native. Mismos tokens de diseño que la app desktop

## Aprendizajes

El problema más inesperado fue la generación de IDs. SQLite no tiene `uuid_generate_v4()`, pero Supabase sí. La solución fue generar IDs locales con `Date.now()-random` en el cliente y dejar que Supabase acepte texto como primary key. Funciona, pero si volviera a empezar evaluaría usar `crypto.randomUUID()` del runtime de React Native.

Lo que más aprendí: offline-first no es "guardar en cache". Es repensar toda la arquitectura para que la base de datos local sea la fuente de verdad y el servidor sea solo un mecanismo de sincronización. El 80% del esfuerzo está en el sync, no en la UI.
