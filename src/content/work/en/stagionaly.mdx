## The problem

Italian hospitality hires in waves. Every spring hotels, restaurants and beach clubs need cooks, waiters and receptionists for a few months, and workers need a season. Today that happens in group chats and generic job boards that know nothing about meals, lodging or the length of a season. It is also a market with real privacy stakes: a worker should not have their contact data scraped, and an employer should not be flooded by someone they blocked.

## The solution

Stagionaly is my own product: a job board built for seasonal hospitality. Candidates browse offers, apply and chat with employers. Employers manage their venues, publish offers, review applications and talk to candidates. There is an admin side for approving employers and moderating. It is live on the web, the App Store and Google Play, in Italian, English and Spanish.

It is a pnpm monorepo. The web app is Next.js 16 with next-intl and Resend for email, the mobile app is Expo, and both talk to Supabase for auth, Postgres, storage and realtime. Business rules live in the database as much as possible, so the web app and the mobile app cannot disagree.

The screenshots come from a real device with demo data.

## Stack and key decisions

- **Privacy rules as row level security**: roles and ownership are enforced by policies and security-definer helpers, not by the UI. The suite has 112 migrations, and many have pgTAP tests. One test asserts that a candidate who was blocked by an employer cannot fetch that employer's email
- **Public data through narrow RPCs**: anonymous visitors see offers through a function that returns an explicit list of columns, never `select *`. An earlier policy exposed the establishment id, and the function closed that gap on purpose
- **Deletes that cannot lie**: on a table with RLS, a denied `DELETE` returns no error and affects zero rows. Every delete asks for `count: 'exact'` and fails if nothing changed, so the interface never reports a phantom success
- **Push with a single owner per device**: a database webhook on new notifications triggers an edge function that reads the recipient's preferences and sends through Expo. After an incident where one phone was attached to two accounts, a device token now belongs to exactly one user and is claimed through a single transaction
- **Dev first, then production**: every change is a committed migration, merged to a development branch with its own Supabase branch and Vercel preview, verified, and only then promoted. Nobody pushes to the cloud database by hand

<Callout type="warning" title="The silent zero">
  A rejected write that returns "success" is worse than a visible error. Checking the affected row
  count is a one-line habit that removes a whole family of "it said saved but it was not" bugs.
</Callout>

## What I learned

Put privacy where it cannot be bypassed. A UI check protects one screen; a policy with a test protects every client you will ever write.

Test the database like code. pgTAP turns "can this user see that row" into a regression test, and it caught more real mistakes than any end-to-end test.

Production incidents are design input. The push token bug was a data model problem, so the fix was a constraint and a transaction, not a patch in the client.

And a small marketplace is mostly trust. Blocks, approvals and honest empty states matter more to early users than another filter.
