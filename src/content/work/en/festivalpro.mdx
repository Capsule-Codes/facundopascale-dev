## The problem

A music festival needs its own app: a schedule that changes the day of the event, a map, a way to save favorites. But every festival wants its own branding, and about ninety percent of the functionality is the same. Maintaining a codebase per festival means duplicated bugs, features that reach one app late and a manual release for each store. The other extreme, one generic app, loses the identity that organizers pay for.

## The solution

Festival Pro is a mobile app built by Capsule Codes for a client, as a multi-tenant product: one React Native and Expo codebase that ships as two distinct apps, Festival Pro Schedules and Folk Alliance 2026. An `EXPO_PUBLIC_APP_VARIANT` switch in the Expo config loads the configuration for each one, with its own bundle id, icon, splash, deep link scheme and EAS profiles, and its own update channel for over-the-air changes.

Inside each app the festival is data. The user picks an event, and the schedule, the map, the venues and even the tab bar come from a CMS feed. The app only needs to know how to render them.

Expo SDK 54 and React Native 0.81, React Navigation 7 and React Native Paper with Material 3 build the interface. Zustand holds the state and Zod validates everything that comes from outside. The screenshots show public festival content from the apps themselves.

## Stack and key decisions

- **Two apps, one repo**: each variant has its own config, bundle id and scheme, and EAS profiles for development, preview, staging and production, each with a separate channel. A schedule fix reaches one app's users over the air without a store review, and cannot leak into the other
- **A theme derived from one color**: each festival sends a seed color, and a Material 3 palette is generated from it for light and dark modes. An invalid value, such as a URL where a color was expected, falls back to the default instead of breaking the screen, and a set of contrast checks keeps text readable on whatever the festival picked
- **A tab bar from the feed**: the bottom tabs are built from the menu items each festival publishes, which is why one app shows a map and vendors while another does not
- **Offline tolerant by construction**: the feed pipeline reads the cache first and commits what validates, then fetches in parallel unless the device is known to be offline. A failing menu does not hurt its siblings, and an empty response gets a single retry after a short pause
- **A guard against stale writes**: if the user switches festival while a request is in flight, the late result is discarded, so one festival's artists never show up inside another festival's app
- **Zod at the boundary**: both cached and fresh payloads go through the same schema before they reach the store

<Callout type="info" title="Why the stale guard exists">
  Every fetch writes into the same shared stores. In a multi-tenant app a slow response from the
  festival you just left is not a harmless race, it is wrong data on the wrong brand.
</Callout>

## What I learned

Treat the tenant as data and the variant as configuration. Once colors, tabs and content come from the feed, a new festival is mostly content work, and the code stays the same.

Remote data is hostile by default. Validating the cache and the network with the same schema, and allowing partial failure, made the app behave well in venues where the signal is the worst.

Race conditions get more expensive when state is shared. A tiny guard that compares who requested the data with who is selected is cheaper than any amount of debugging at a live event.

What I would change: keep build numbers out of config files and in EAS environment variables from day one, and spend more time earlier on background sync for last-minute schedule changes.
